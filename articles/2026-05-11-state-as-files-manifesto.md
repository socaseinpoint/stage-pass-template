# State-as-Files: манифест для работы с агентами на длинных задачах

Открываешь новую сессию с AI-агентом. Контекст из прошлой — пустой. Опять объясняешь зачем, почему, что уже сделано, какое решение приняли по третьему пункту. Час потерян до первой полезной задачи.

Это норма? Нет. Это симптом одного простого антипаттерна: state живёт в чате.

## Чат как память — где это ломается

Чат удобный. Пишешь — агент отвечает — всё в потоке. На коротких задачах работает идеально.

Но чат — эфемерная штука. И как только задача перестаёт укладываться в одну сессию, начинаются потери:

- Сессия закрылась — state потерян.
- Контекст-окно переполнилось — state частично потерян (и хуже всего: ты не знаешь какая часть выпала).
- Другой агент — state полностью потерян.
- Коллега подхватывает работу — у него нет твоего state.
- Прошёл день — твоя собственная голова забыла state.

Большие задачи (аудит кодовой базы из четырёх сервисов, миграция 18 тысяч записей, литературный обзор 80 пейперов, оценка проекта на сотни стори перед дедлайном) **не помещаются в одну сессию**. Никогда. Они идут днями, неделями, иногда месяцами. И каждая новая сессия — это потеря.

Симптомы знакомы:

- «Я же это уже спрашивал на прошлой неделе»
- «Подожди, какое решение мы приняли по X?»
- «Агент не понимает что у нас уже сделано»
- «Чувак, мы это уже обсуждали — открой чат от вторника»
- Дрейф в интерпретациях — каждая сессия чуть-чуть переписывает решения, незаметно

Хуже всего: ошибки не громкие. Никто не падает с traceback. Просто проект медленно гниёт под слоем «забыл», «передоговорил», «начал с другой стороны». Через две недели уже непонятно где ты и что трастворти.

## Идея: state в файлах, чат живой

Параллель из мира кода. Git существует 20 лет. И мы давно перестали спорить о том, что код живёт в файлах, а не в state IDE. IDE — рабочий инструмент. Файлы — single source of truth. Закрыл IDE → ничего не потерял. Открыл другой → продолжил. Шаришь с коллегой → шаришь файлы, не свой workspace.

Тот же принцип для агентских задач:

- **Чат** — живая рабочая память **внутри одной сессии**. Туда-сюда, итерации, мышление вслух.
- **Файлы** — память **между сессиями**. Цель проекта, план стадий, stage-plan'ы, артефакты, blockers — всё под git history.

Чат не убивается. Он остаётся живым рабочим инструментом. Но когда сессия закончится, ничего важного в нём не оставлено. Всё — в файлах. Следующая сессия (твоя, другого агента, коллеги) открывает файлы и продолжает.

Это и есть state-as-files. Дальше — конкретика как это устроить.

## Принципы

### 1. Цель проекта в плане, под версией

Первая строка плана — цель проекта. Одной фразой, **измеримая**. Не «улучшить onboarding», а «снизить drop-off на step 3 с 40% до 25%». Не «расчистить требования», а «расклассифицировать 1200 стори на keep/kill/fix к 13 мая». Измеримость — это способ проверить «финиш». Без неё агент не понимает когда работа закончена, дрейфует или зацикливается.

Никаких «обсудим позже», «примерно понятно», «разберёмся в процессе». Goal явная, в файле, читается за две секунды.

Что это даёт. Любая сессия — твоя завтрашняя, другого агента, коллеги — начинается с чтения цели. Никто не теряется в «что мы вообще делаем». Агент не дрейфует через пять сессий в соседнюю задачу. Финал проекта сверяется с тем что записано на первой строке, а не с твоей трактовкой цели после трёх недель работы.

Меняется цель — пишешь `PLAN-v2.md` с явным diff vs v1 в шапке: «добавлена стадия S-05 — сошлись после ревью с PM 2026-05-11». v1 не правишь, не удаляешь, оставляешь в архиве. README указывает на текущую версию. Смена цели — осознанный акт, под git history, на двух строках diff'а.

То же правило применяется ко всему плану: стадии, exit criteria, constraints. План — стратегический snapshot, замороженный per version. Мутирующий план гниёт: подстадии множатся (`S-04` → `S-04a` → `S-04b`), маркеры статуса противоречат реальности, через две недели документу никто не доверяет. Иммутабельность — это то, что сохраняет trust к v1 в момент финикса. Стоит редко (большинство проектов едут на v1 до конца). Зато v1 всегда работающий снапшот.

### 2. Один stage-plan = одна сессия handoff

Каждая сессия производит ровно **один** stage-plan для следующего агента (или для тебя завтра). Никогда не «обновлю старый SP» — это рецепт превратить snapshot в мутирующий документ.

```
Agent A финиширует → пишет SP-003 → Agent B
читает PLAN-current + SP-003 → выполняет →
пишет artifacts + новый SP-004 для агента C
```

ID-конвенция: `SP-001`, `SP-002`, `SP-003` — сквозной глобальный счётчик через весь проект. Параллельные ветки работы кодируются через поле `Scope:` в шапке SP, не через побитие нумерации.

В шапке SP — короткий контекст для следующего агента: что предыдущий узнал, что решил, на что наткнулся. 5-15 строк. Этого хватает чтобы открыть холодную сессию и не задавать «погоди, а зачем мы это вообще делаем».

### 3. Verify block в конце каждого прохода

Артефакт без verify block — недоделанный артефакт. В конце пасса обязательно:

- Total items processed: N
- Counts by bucket / class / label: ...
- 3 random samples цитата with ID

Зачем. Counts ловят fan-out баги. Если пасс обработал 480 из 500 — увидишь сразу. Без verify это всплывёт через два пасса вниз по течению, когда дебажить уже мучительно.

Samples ловят silent misclassification. Reviewer читает три ID, решает — доверять ли всему батчу. Без samples первая ошибка обнаружится только в финале, когда переделывать поздно.

Это дёшево (5 строк в конце артефакта) и спасает часами в долгосрочке.

### 4. Один пасс = одна линза

Не миксуй пассы. Дедупликация — отдельный пасс. Классификация — отдельный пасс. Code review — отдельный пасс. Никогда «заодно почищу мусор пока тут сижу».

Почему. Смешанный пасс непроверяем. Ревьюер не может прочитать 500-item mixed-lens output и доверять чему-либо. Diff становится нечитаемым. Хуже того: ошибки одной линзы прячут ошибки другой. Когда что-то идёт не так — непонятно из какой логики пришло.

Single-lens пассы дают чистые, сравнимые диффы и recoverable failures. Это не педантизм, это инженерия.

### 5. Hard time-box per pass

Запланировал пасс на 90 минут — закрывай через 90 минут. Не успел — записываешь остаток в handoff и открываешь новый SP под продолжение.

Зачем. Переезжающие пассы превращаются в multi-lens пассы — оператор молча добавляет «пока я тут» работу. Либо в context-window failures — агент исчерпывает рабочую память и начинает галлюцинировать. Жёсткий time-box оставляет каждый пасс чистым.

### 6. Commits как часть протокола

Каждый закрытый SP — commit. Каждая батч артефактов — commit. Bump плана — commit с diff'ом в теле.

```
[SP-007] close: dep-update service-d
[SP-007] A-01..A-02: dep audit + apply log
[SP-006] close: dep-update service-c
[PLAN-v2] bump from v1: added dep-update stage
[blocker] domain: license-X compatibility?
[SP-005] close: dep-update service-b
...
```

`git log --oneline` читается как handoff timeline. Новый агент скроллит лог — это **весь project narrative в 20 строк**. Без статус-доков, без weekly updates, без сторителлинга. История уже есть.

### 7. Coupling через ID, не через гиперссылки

В PLAN не ставь ссылок на stage-plan'ы. Никаких `[See SP-003](../stage-plan/SP-003.md)` в теле плана. Только текст: `См. SP-003`.

Зачем. Планы эволюционируют, SPы splитятся, ссылки гниют. `PLAN-v1` ссылался на `SP-003`, потом SP-003 superseded by SP-007 — линк сломан. Диф между версиями плана зашумлён link churn вместо изменений стратегии.

ID-only coupling стабилен. Grep по `SP-003` находит и текущий стейт в любом инструменте. ID живёт дольше пути в файловой системе.

### 8. Frozen state families

Если у тебя есть классификация (priority-*, severity-*, kind-*) — после стадии где она проставлена, ярлык **замораживается**. Перевешивать без явной записи в apply-log запрещено.

Почему. Если `severity-high` может откатиться обратно через две стадии — каждый downstream пасс должен перепроверять весь батч. Стоимость поздно связанного state в фан-ауте огромна. Замораживание — это то, что позволяет `S-05` доверять выводам `S-03` без повторного прогона.

Escape hatch остаётся: перевесить ярлык можно, но через явное решение в apply-log. Делиберативно. Записано. Не «случайно».

## Антипаттерны

| Антипаттерн | Что ломается | Фикс |
|---|---|---|
| «Я просто обновлю PLAN.md по месту» | Trust в PLAN исчезает; diff потерян | Написать PLAN-vN+1, архив vN |
| «Этот пасс заодно почистит мусор» | Ошибки прячутся; diff нечитаем | Чистка — свой пасс |
| «Маленький пасс, verify block пропущу» | Fan-out баги всплывают через три пасса | Verify block всегда |
| «SP затянулся, продлю его на сегодня» | Stale handoff; multi-lens drift | Close as done с overflow note; новый SP |
| «PLAN-v1 ссылается на SP-003 § Findings» | Link rot при supersede | Reference by ID в прозе |
| «Перевешу несколько без записи» | Downstream не может доверять upstream | Apply-log decision entry первым |
| «Я помню в чате что мы решили» | Следующая сессия теряет контекст | Записать в SP или HANDOFF.json |

## Готовый шаблон

Я собрал всё это в шаблон-репо: **[github.com/socaseinpoint/stage-pass-template](https://github.com/socaseinpoint/stage-pass-template)**.

Внутри:

- Структура директорий (`plans/`, `stage-plan/`, `artifacts/`, `workspace/`, `.planning/`)
- Шаблоны (`_template.md` для PLAN, SP, артефактов)
- `CLAUDE.md` заготовка — заполняешь под свой проект (state families, gotchas, workspace policy)
- `docs/PROTOCOL.md` — спецификация фреймворка
- `docs/WHY.md` — рационализация каждого правила + таблица антипаттернов
- Три абстрактных примера сценариев (codebase audit, data migration, research review) — каждый показывает как протокол ложится на конкретный класс задач

Минимальный цикл:

```bash
# 1. Клонировать шаблон под свой проект
git clone https://github.com/socaseinpoint/stage-pass-template.git my-project
cd my-project
rm -rf .git && git init   # начать свою историю

# 2. Заполнить конвенции
$EDITOR CLAUDE.md         # заменить <...> placeholders
                          # state families, workspace policy, gotchas

# 3. Написать первую версию плана
cp plans/_template.md plans/PLAN-v1.md
$EDITOR plans/PLAN-v1.md
$EDITOR plans/PLAN-current.md   # указать на PLAN-v1.md

# 4. Открыть первую сессию-handoff
cp stage-plan/_template.md stage-plan/SP-001-collect-inputs.md
$EDITOR stage-plan/SP-001-collect-inputs.md

# 5. Работать. Складывать артефакты по ходу пасса.
mkdir -p artifacts/SP-001
$EDITOR artifacts/SP-001/A-01-inventory.md
$EDITOR artifacts/SP-001/A-02-apply-log.md   # verify block здесь

# 6. Закрыть SP коммитом (sp status → done)
git add -A
git commit -m "[SP-001] close: collect inputs"

# 7. Следующая сессия — новый SP, тот же цикл
cp stage-plan/_template.md stage-plan/SP-002-classify.md
```

Через 3-4 SP цикл становится автоматическим. Через 10 — `git log --oneline` уже читается как карта проекта.

## Где есть ценность

Фреймворк имеет смысл на пересечении трёх условий. Все три должны выполняться одновременно — уберёшь одно, и протокол превращается в overhead.

1. **Цель измеримая.** Есть способ проверить «дошли или нет». «Снизить latency P95 на 30%», «расклассифицировать 18к стори в шесть бакетов», «оценить проект к 13 мая». Без измеримости агент не знает когда финиш — дрейфует или зацикливается.

2. **Много итераций с агентами.** Задача не вмещается в одну сессию. Дни, недели, иногда месяцы. Несколько агентов в цепочке либо ты-завтра как «другой агент». Если хватает одной сессии — handoff не нужен, фреймворк лишний.

3. **Каждый шаг через ручную валидацию.** Verify block, ревью артефактов, явное закрытие SP человеком. Это **supervised agent work**, не autonomous loop. Хочешь полную автономию без человека в петле — это другой шаблон.

Типовые задачи в зоне ценности: аудиты кодовой базы, миграции данных, многопроходная классификация, эстимейты крупных скоупов, ресёрч-обзоры, долгие рефакторы.

Уберёшь измеримость — агент дрейфует. Уберёшь итеративность — overhead не оправдан. Уберёшь ручную валидацию — silent errors накапливаются. Все три или ничего.

## Финал

Идея простая. State в файлах, чат живой. Git и его апологеты делают это с кодом 20 лет — никто давно не спорит. Для работы с AI-агентами на длинных задачах это так же критично — потому что агенты помнят прошлую сессию **ещё хуже** чем люди.

Чат — рабочая память. Файлы — память между сессиями. Когда чат умирает, работа не должна умирать вместе с ним.
